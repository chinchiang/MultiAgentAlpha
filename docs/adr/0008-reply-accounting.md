# Reply accounting: one module turns every exchange's record into the audit counters, and the context agent's canary echoes are counted apart

The **reply outcome** of every exchange is classified once (docs/adr/0001-reply-outcome-accounting.md), but how it was counted was spread over five agents, `mara.exchange` and the pipeline. Each agent compressed the outcome into error strings (`"refused"`, `"canary_echoed"`, `"truncated"`, provider codes, `"invalid_item:…"`, coverage codes and two summary markers) and returned them in a positional tuple whose meaning changed by role; the pipeline decoded them back with `_ERROR_MARKERS`, `_retryable`, `_count_invalid`, `_count_ballot` and two key-to-counter tables; ADR 0001's rule that an empty reply is read by role lived half in `exchange.extraction_flags` and half in `exchange.parse_items`; and the only check that every failure counter makes the review incomplete was a test reading `pipeline.py` as text. Two errors had come out of it. The context agent wrote its canary echoes and reports into the reviewers' `canary_echoes` and `canary_reports`, so calibration's reviewer canary rate (`canary_echoes / reviewer_calls`) counted a context echo against that family's reviewers. And the skeptic, red team and judge item counts were written per family only, past `Audit.add`, so they had no total.

The accounting now lives in one module, `mara.audit`, which already held `Audit` and `INCOMPLETE_COUNTERS`. Every exchange gives one **reply record**: the role, the family, the reply outcome kind (`exchange.KINDS`), its canary echoes and canary reports, the number of invalid items, whether the reply was voided as a whole, the role's own counts under local names (unverified quotes, unverified controls, refuted, exploit code stripped, and the like), the tokens, and detail codes that only the log reads. An agent returns its items and the records of its exchanges; the context agent returns one record per bundle batch rather than summing them itself. The module owns a table that, for each role, says whether it is an extraction role or a ballot role, which local names it may use, the persisted counter name of each, and whether a non-zero value makes the review incomplete. A local name the table does not declare is an error. How each reply outcome counts for a role, an empty reply included, is read from this table only; `exchange.classify` still decides the outcome, `extraction_flags` is removed, and `parse_items` returns the items and an invalid count. `INCOMPLETE_COUNTERS` is derived from the table, in the table's order, which keeps the order of the incomplete reasons the review status writes (docs/adr/0007-review-status-and-gate.md) and the set the score summary's allowlist imports (docs/adr/0004-score-summary.md). The module also reads the per-family encoding (`name[family]`) back, so calibration no longer splits keys itself, and it gives the log tags (`[REFUSED]`, `[CANARY ECHOED]`, …) from the record. Whether a voided reply is worth one more call is the module's rule; the retry loop stays in the pipeline until the ballot round itself is reworked.

The persisted counter names do not change, irregular ones included (`invalid_findings_dropped`, `findings_with_unverified_quotes`): the table is the one place that knows them. There are two exceptions. The context agent's canary counters become `context_canary_echoes`, which makes the review incomplete like every canary echo, and `context_canary_reports`, which does not; `canary_echoes` and `canary_reports` count reviewer replies only, as they did before the context agent existed. And `skeptic_items`, `redteam_items` and `judge_items` gain their totals. `EXCHANGE_VERSION` rises to 5 for both: `canary_echoes` means something else from this version, so calibration compares its trends only within one version, as ADR 0001 already requires. A version 4 report keeps its mixed `canary_echoes`. Everything else stays as it was: the same replies are retried (truncated, unparseable, empty and incompletely covering replies once; refusals, provider errors and canary echoes never), tokens are counted in total only, and `*_unparseable_replies`, `*_retries` and `*_calls` do not make a review incomplete. One edge follows from reading every reply as its outcome kind: a skeptic or red-team reply without an item list that also echoes the canary (a refusal, an empty reply or an unparseable one) counted only the echo; it now also counts as its outcome, as a reviewer's or the context agent's always did: one more `*_refusals`, `*_invalid_items`, or `*_unparseable_replies` and `*_invalid_items`. The echo already made such a review incomplete, so the review status does not change. The order in which `report.md` lists the audit may change, since the audit is written in a different order; nothing reads that order.

The tests check the module, not the source text. For every role and every reply outcome kind, a record of any kind but ok makes the review incomplete, and an ok record with no counts does not; for every role that carries a canary, an echo makes the review incomplete and a report does not; an undeclared local name is refused; and the derived `INCOMPLETE_COUNTERS` is the old tuple with `context_canary_echoes` added and the old codes in their old order. Two further tests pin the fixes: a context echo does not reach calibration's reviewer canary rate, and the item counts have totals. Tests about how the pipeline reacts to a reply build records directly; tests about an agent's own checks (coverage, the canary screen, exploit-code stripping) go through the agent with a fake provider returning a `RawReply`. The change ships as one pull request, so the exchange version rises once, and its description compares the `bias_audit` of one mock review before and after: it may differ only by the declared changes above.

## Considered options

- **Rename every counter to `<role>_<kind>`:** rejected. Calibration, the markdown report and the score summary would need a second read path for every report written before; the table keeps the irregular names in one place instead.
- **Keep the error strings and only move their decoding into the module:** rejected. The string round trip between the agents and the counters, which is what spread the rules, would stay.
- **One record per agent call:** rejected. The context agent makes one exchange per bundle batch and would keep summing its own counters; adding up belongs to the module.
- **A record type per role, or one record with every role's fields:** rejected. Five types widen the interface; one wide record lets a role set a count that is not its own. Local names checked against the table give neither.
- **Keep the empty-reply rule in `mara.exchange`:** rejected. The same reply outcome would be read in two modules.
- **Keep `INCOMPLETE_COUNTERS` hand-written beside the table:** rejected. It would be a second list to keep in step, which is what the source-reading test was there for.
- **Move the retry loop into the module now:** rejected. The loop belongs to the ballot round, and the module's interface would have to take callables only to give them up again.
- **Fix the context canary counters and the item totals in a pull request of their own first:** rejected. The exchange version would rise twice for one rework.
- **A golden `bias_audit` file as a permanent test:** rejected. It would be regenerated on every intended counter change and stop checking anything; the before-and-after comparison is made once, for this change.
