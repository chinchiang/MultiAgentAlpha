# Score summary: an explicit export, built from an allowlist, is all that leaves an in-country pipeline

Report chapter 26 (CN-3) says the global security team receives only the dimension scores of an in-country review, never finding detail; detail that must cross the border goes through the DSL and PIPL export assessment. Every output `mara review` writes (report.md, report.json, report.sarif, the human queue, PSIRT payloads) carries finding detail, and the in-country team needs all of it (CN-1). So the review keeps writing everything, and a separate command, `mara export-summary <report.json>`, derives a **score summary** from a report already written: the act of sending something abroad is one explicit step that can be run on any retained report.

The summary is built from an allowlist, never by deleting fields from the report. `ReviewReport` keeps growing (v0.6.0 added the human-resolution fields), and with a denylist every new field would cross the border by default; with an allowlist a field crosses only once someone adds it on purpose, and a test pins the key set. The allowlist holds the summary's own provenance (`schema`, `source_report_sha256`, `exported_at`), what was reviewed (`target_pseudonym`, `revision_pseudonym`, `pseudonym_key_id`, `review_scope`, an optional operator-given `label`), how (`generated_at`, `provider_mode`, `families_used`, `config_hash`), the outcome (`review_status`, `incomplete_reasons`, `gate_passed`) and the scores (`overall_score`, and per dimension its name, score, counts and whether a tool ran). Per-dimension counts follow the final outcome, as the scores do (docs/adr/0003-human-resolution.md). The report's `target` path is left out because a local path can name the repository and its layout; counts by evidence tier or severity are left out because they come closer to pointing at single findings than CN-3's "dimension scores" allows. `source_report_sha256` lets the in-country team show which retained report a summary came from without the hash revealing anything. Apart from the label, no free text crosses: every allowlisted string must have the shape its field always has (known incomplete-review codes, model families, dimensions and provider modes, an ISO timestamp, a SHA-256 config hash), and a report that holds anything else is refused, because a hand-edited report can validate as a `ReviewReport` and still carry text in those fields. A dimension's free-text note is not exported: what it says today follows from whether a tool ran.

The export fails closed: a report that does not validate as a `ReviewReport` produces nothing, a mock-mode report is refused unless `--allow-mock` is given (its scores describe seeded material and would read as a site's real scores), a label must be 1 to 80 code points of letters, marks, numbers, punctuation, symbols and spaces (including the full-width space), with at least one that is not a space and none at either end, and no control or format character (zero-width joiners and bidirectional controls included, at the cost of emoji built with them), and the summary may neither replace the report it is made from (the evidence `source_report_sha256` names) nor land inside the reviewed target. A report whose target is a relative path is refused, since where it points would depend on the directory the export runs in. Only the output is checked against the target: the export reads no config and runs no tool, so where the workspace lies does not matter to it. MARA cannot judge what a label says; its content is the operator's responsibility. An incomplete review is still exported, with `overall_score` null and its reasons: hiding that a site's review did not finish would be worse than showing it.

Who was reviewed crosses only as **summary pseudonyms**. The report's `target_id` is an unkeyed SHA-256 of the repository's origin URL and path, so anyone abroad holding a list of candidate repositories could confirm which one a summary is about, and a commit SHA can name the repository through any mirror outside the country; either would undo the decision that only the operator, through `--label`, names the target. The summary therefore carries HMAC-SHA256 pseudonyms under a key from `MARA_SUMMARY_KEY` (at least 32 characters, no surrounding whitespace): one for the target and one for the revision bound to that target, so forks sharing a commit are not linked, and null when the report has no revision. The same key gives the same pseudonyms on every export, so the receiving team can follow a target over time; `pseudonym_key_id` (the first 16 hex digits of the key's SHA-256) tells it when the key changed. The key stays in the country and never travels with a summary; the in-country team maps a pseudonym back by exporting its retained report again under the same key. Without a usable key, or for a report with no `target_id`, nothing is exported.

Reports now record their **review scope** (`full` or `incremental`), because an incremental review's scores cover only the increment and cannot be compared with a full review's. Reports written before the field existed read as `unknown` rather than being refused or guessed as full.

## Considered options

- **`mara review --summary-only`:** rejected. The in-country team would lose the detail it needs, and the detail is what CN-1 keeps in the country, not what CN-3 removes.
- **Always write a summary next to every report:** rejected. A file would appear on every review host with no step that marks it as the thing sent abroad.
- **A detail export behind an approval reference:** rejected. Detail that passed the export assessment is handled by legal in the approved way; MARA opening a path for it would make the assessment look optional.
- **Export the report's `target_id` and `revision` as they are:** rejected. Unkeyed, they can be confirmed from a list of candidate repositories or a mirror, which names the target without the operator deciding to.
- **Leave the target out entirely, or give it a fresh random id on each export:** rejected. The receiving team could no longer tell two sites' repositories apart or follow one over time.
- **Accept any printable label (`str.isprintable`):** rejected. It refuses the full-width space an operator types in a Chinese name and accepts a label of spaces only.
- **A policy (P9) that forbids offshore outputs such as GitHub issue tickets in an in-country config:** left to CN-1. CN-3 only makes a summary that is safe to send; what else an in-country pipeline sends abroad is CN-1's question.
