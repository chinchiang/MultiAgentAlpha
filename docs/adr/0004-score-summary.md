# Score summary: an explicit export, built from an allowlist, is all that leaves an in-country pipeline

Report chapter 26 (CN-3) says the global security team receives only the dimension scores of an in-country review, never finding detail; detail that must cross the border goes through the DSL and PIPL export assessment. Every output `mara review` writes (report.md, report.json, report.sarif, the human queue, PSIRT payloads) carries finding detail, and the in-country team needs all of it (CN-1). So the review keeps writing everything, and a separate command, `mara export-summary <report.json>`, derives a **score summary** from a report already written: the act of sending something abroad is one explicit step that can be run on any retained report.

The summary is built from an allowlist, never by deleting fields from the report. `ReviewReport` keeps growing (v0.6.0 added the human-resolution fields), and with a denylist every new field would cross the border by default; with an allowlist a field crosses only once someone adds it on purpose, and a test pins the key set. The allowlist holds the summary's own provenance (`schema`, `source_report_sha256`, `exported_at`), what was reviewed (`target_id`, `revision`, `review_scope`, an optional operator-given `label`), how (`generated_at`, `provider_mode`, `families_used`, `config_hash`), the outcome (`review_status`, `incomplete_reasons`, `gate_passed`) and the scores (`overall_score`, `dimensions`). Per-dimension counts follow the final outcome, as the scores do (docs/adr/0003-human-resolution.md). The report's `target` path is left out because a local path can name the repository and its layout; counts by evidence tier or severity are left out because they come closer to pointing at single findings than CN-3's "dimension scores" allows. `source_report_sha256` lets the in-country team show which retained report a summary came from without the hash revealing anything.

The export fails closed: a report that does not validate as a `ReviewReport` produces nothing, a mock-mode report is refused unless `--allow-mock` is given (its scores describe seeded material and would read as a site's real scores), a label must be one line of 1 to 80 characters, and the summary may neither replace the report it is made from (the evidence `source_report_sha256` names) nor land inside the reviewed target. Only the output is checked against the target: the export reads no config and runs no tool, so where the workspace lies does not matter to it. MARA cannot judge what a label says; its content is the operator's responsibility. An incomplete review is still exported, with `overall_score` null and its reasons: hiding that a site's review did not finish would be worse than showing it.

Reports now record their **review scope** (`full` or `incremental`), because an incremental review's scores cover only the increment and cannot be compared with a full review's. Reports written before the field existed read as `unknown` rather than being refused or guessed as full.

## Considered options

- **`mara review --summary-only`:** rejected. The in-country team would lose the detail it needs, and the detail is what CN-1 keeps in the country, not what CN-3 removes.
- **Always write a summary next to every report:** rejected. A file would appear on every review host with no step that marks it as the thing sent abroad.
- **A detail export behind an approval reference:** rejected. Detail that passed the export assessment is handled by legal in the approved way; MARA opening a path for it would make the assessment look optional.
- **A policy (P9) that forbids offshore outputs such as GitHub issue tickets in an in-country config:** left to CN-1. CN-3 only makes a summary that is safe to send; what else an in-country pipeline sends abroad is CN-1's question.
