# Local web workbench: a loopback server from the standard library that runs `mara review` as a subprocess and only reads what it writes

MARA had no way to follow a review while it ran, to keep more than the last one, or to see whether the L0 tools and model endpoints were ready without reading files. `mara serve` adds a **workbench**: a local web page in Traditional Chinese and English to start a white-box review, follow its nine stages, read its findings, roles, models and gaps, and check the tools, the trivy database and every config's policies. It is a view on the existing command line, not a second way to review.

**Reviews run as `mara review` subprocesses.** Each **run** is one `mara review` child process with its own output directory, `<out>/runs/<run-id>/`, holding the reports the command line writes plus `run.json` (the request, the argv, the roles and models of the config at launch, status and exit code), `run.log` (the child's output) and `progress.json`. Every refusal of the command line still decides: `workspace.check_outside` with the config, output, evidence and progress paths, the policies P1 to P8 when the config loads, and the mock/live consistency check. The server repeats those checks before it starts the child, only so that the page can name the refusal; it never weakens one. The PSIRT options (`--notify-psirt`, `--psirt-event`) are not offered, because they start EU CRA Article 14 clocks and stay a deliberate command-line step. One review runs at a time, and never while an environment job replaces the tools or the trivy database it uses (nor such a job while a review runs). Stopping the server, by Ctrl-C, SIGTERM or SIGHUP, cancels a running review rather than leaving it orphaned: the children run in their own process groups, so the server stops them itself, and it closes the progress record a killed child left open.

**The pipeline reports its stages to a progress record.** `mara review --progress-file PATH` hands `Pipeline` a `mara.progress.Progress`, which rewrites PATH atomically at every stage boundary and every pipeline log line: bundle, tools, context, reviewers, skeptic, red team, jury, scoring, report. The CLI marks the record finished only after it has written every report, and failed on any exception. This matters because the exit code alone is ambiguous: 2 is both an enforced gate and a usage error. A run is therefore finished only when its progress record says so. The progress record is a view, never evidence: nothing reads it back into a report, and a record that cannot be written is logged and skipped.

**The page derives nothing.** The server reads `report.json` through `ReviewReport`, so the jury outcome and the final outcome on the page are the `ConsensusResult` properties of docs/adr/0005-jury-outcome.md, not a second implementation in JavaScript. Credentials appear by environment-variable name and presence only, never by value.

**Access is loopback only, with a token in a header, never in a cookie.** The server listens on 127.0.0.1, localhost or ::1 and refuses any other address. Finding detail must stay where the review ran (CN-3, docs/adr/0004-score-summary.md), and a remote workbench is reached through an SSH tunnel. The URL `mara serve` prints carries a random token that lives as long as the server, in its fragment (`#token=...`), which no server, log or Referer sees. The page moves it out of the address bar into this origin's localStorage and sends it in an `X-MARA-Token` header with every API call, downloads included. A cookie would have been simpler and is not used: browsers send a cookie to every service on 127.0.0.1 whatever its port, so a listener another local user runs could collect it, while localStorage is scoped to scheme, host and port. The header is also the CSRF defence, since another origin can neither read the token nor send the header without a CORS preflight, and the server sends no CORS headers. It refuses a Host header that does not name the loopback server, which defeats DNS rebinding, and an Origin or Sec-Fetch-Site from another site. The page itself holds no data and is served without the token. When `mara serve` opens the browser, it opens a redirect file only the user can read, never the URL itself: a process's arguments are visible to every local user, and a browser keeps its own as long as it runs. Signing out makes the browser forget the token; the printed URL works until the server stops.

**The page is one self-contained document.** The server assembles it at start-up from the packaged template, stylesheet, script and dictionaries. Its Content-Security-Policy allows exactly that script and that stylesheet by SHA-256, `connect-src 'self'` and nothing else, with `require-trusted-types-for 'script'`. The policy is built at runtime and is not a literal in any file, so `scripts/csp_ci.py` cannot see it. `tests/test_web_static.py` checks its directives against the hashes of the assembled page everywhere, and grades it with the pinned csp-evaluator where that is installed under `.mara-tools`. The CI tests job installs csp-evaluator next to gitleaks, semgrep and semgrep-rules for this, so every pull request grades the served policy (and `tests/test_tools_csp.py` runs its real-package check there too). The script builds the DOM only through element and text APIs, so repository-derived text (titles, quotes, arguments) is always text.

**A read-only demo is published, the workbench is not.** `docs/workbench/index.html` on GitHub Pages is the same page with a `demo` data block: the server's answers to every GET the page makes, captured by `scripts/build_workbench_demo.py` from one offline review of the seeded fixture by the mock providers through a real in-process server. In it the script answers its API calls from that block, refuses every change (starting, cancelling or rerunning a review, a job, a setting) and makes no request at all. It is compatible with CN-3 because there is nothing to keep in the country: the reviewed code is the repository's own synthetic fixture and no model is called. The capture keeps only `config/mara.mock.yaml`, drops model endpoints, replaces the paths and the kernel of the machine that made it, and fails rather than publish anything else. GitHub Pages sends no headers, so its policy is a meta element (the served policy without `connect-src` and `frame-ancestors`), which the repository's own `scripts/csp_ci.py` scan grades. The served page never carries a data block.

## Considered options

- **FastAPI or Flask with a JavaScript framework and a build step:** rejected. Every runtime and development dependency is a hash-locked closure relocked by hand and scanned with no advisory exceptions. A web stack would add dozens of distributions to that closure and an npm toolchain outside it, for a page that needs neither.
- **Run the pipeline in the server process:** rejected. Cancelling a synchronous review needs a separate process. A crash or a provider hang would take the server down. And the command line's checks would have to be repeated rather than reused.
- **Parse `pipeline.log` or the console output for progress:** rejected. `pipeline.log` is written only once the review ends, and console text is not a contract.
- **A static HTML report per run (no server):** rejected as the whole answer. It cannot start a review, follow one, or check the environment. The Markdown and SARIF reports remain the record a run leaves.
- **Edit `config/mara.yaml` from the page:** deferred. The config is policy-checked YAML whose comments carry review history; the page shows every config's models, data residency and policy results, and `mara check-config` runs as a job.
- **Publish the workbench itself (a hosted service) rather than a demo:** rejected, for the CN-3 reason above and because a shared service needs accounts, TLS and access control this design does not have. The read-only demo shows the page without any of that.
- **Listen on all interfaces behind a password:** rejected, for the CN-3 reason above. A password would also be a second credential to manage, for a tool one person runs on their own machine.
- **An HttpOnly session cookie with a CSRF header:** rejected after review. The cookie reaches every port on 127.0.0.1, and one unparseable cookie from another local application made Python's cookie parser drop them all.

## Consequences

- `Pipeline` takes an optional `progress`. Without one, every call is a no-op, so existing callers and tests are unchanged. `pipeline.log` is still written at the end, as before.
- New runtime code lives in `mara.web` and uses only the standard library and the existing dependencies. The static files are package data, and `tests/test_web_static.py` fails when one would be missing from a wheel.
- `tools/semgrep-triage.yaml` gains one entry: the workbench starts children only as argv lists after validating every value. The template uses plain `__MARA_*__` markers rather than `{{...}}`, which semgrep's template-injection rules would read as a template language.
- The demo goes stale whenever the page's script, stylesheet, dictionaries or the version change: `tests/test_workbench_demo.py` re-assembles it around the committed snapshot and fails until `scripts/build_workbench_demo.py` is run and its output committed. Its data block shows each human-queue item's key (`v2-` and 24 hex digits), which gitleaks' generic rule took for an API key; `.gitleaks.toml` allowlists exactly that format. JSON data blocks escape `{{` and `{%` so that no quoted fixture template reads as one to semgrep.
- Runs and jobs accumulate under `<out>/runs/` and `<out>/jobs/`, which are git-ignored. Deleting old ones is the operator's task; the workbench never deletes a run.
- The maintenance actions (install the locked tools, download the trivy database) run the workspace's own `scripts/`, which an installed package does not contain. In such a workspace the page disables them and says why.
