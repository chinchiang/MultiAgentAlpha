# 第八部　實務應用

## 第 21 章　跨國 ODM/EMS 的部署拓樸

### 21.1 共用管線：台北、桃園、休士頓、Brno/Blučina

這四個廠區可以共用同一條管線，拓樸如第 8 章的圖。雛型自 v0.4.2 起的正式面板是：Claude（Opus 5.5）經 AWS Bedrock 的 `global.` 跨區推論設定檔呼叫（ZDR 只涵蓋 Anthropic 自己擔任資料處理者的管道，經 Bedrock 時由 AWS 處理資料【已證實｜B81】；`global.` 設定檔可能在任一 AWS 商用區域處理，合約要求固定區域的廠區應改用地理範圍的設定檔【已證實｜B138】），Gemini 經 Gemini API 付費層呼叫（廠商有限期保留、附核准單號），GLM 自架於 IEC 網路內並以私有 DNS 區 `.iec.inventec` 提供端點，冷備援的 DeepSeek 同樣自架；GitHub Enterprise 的 runner 部署於各廠區網段，L0 工具在本地跑，SARIF 上傳到中央的 code scanning。Brno 廠區另需注意 EU CRA 的時程：第 14 條的 24 小時預警義務已於 2026 年 9 月 11 日生效，通報須經 ENISA 的 Single Reporting Platform 提交【已證實（生效日期與 SRP）｜C11.9、C11.15】，審查管線產出的 A 級 Critical finding 若涉及已出貨產品，應自動交給 PSIRT 作為內部交接；是否構成須通報的事件、法定期限從何時起算，由 PSIRT 確認後決定，審查完成時間不等於知悉時間（雛型已實作此交接，預設關閉）。

### 21.2 隔離管線：上海浦東與重慶

中國廠區依 CSL、DSL 與 PIPL 的資料出境規則單獨處理，不得併入全球的 action item。具體的設計是：

- 原始碼不出境。上海與重慶的 repo 在境內的 GitHub Enterprise Server 或 GitLab 實例，runner 在境內，L0 工具在境內跑。
- 三個家族全部地端。正式面板的 Claude 與 Gemini 都不可用（兩者的 API 都在境外），改以境內自架的開源模型替代；DeepSeek 與 GLM 在境內自架反而沒有出境問題，但仍適用第 13 章第 14 項的校準要求；Nemotron 以 NIM 在境內部署（雛型的境內範例設定即為 DeepSeek 與 Nemotron）。家族數因此可能只剩兩個，第 13 章第 7 項的脆弱性在此更嚴重，人工佇列的門檻應收緊（雛型的境內範例設定即為兩家族，須寫明縮編理由才能通過設定檢查，人工佇列門檻由 0.4 提高為 0.5）。
- 校準集分開。境內管線的校準資料不與全球管線合併，除非經過資料出境的合規評估。
- 報告分開。SARIF 與 Markdown 報告留在境內；全球安全團隊看到的是彙總的面向分數，不是 finding 明細。

這些規則使境內管線的能力低於全球管線（家族少、模型弱、無跨境的校準資料）。這是法律隔離的代價，報告不假裝它不存在。

### 21.3 客戶稽核時的說明

客戶問「你們用哪個模型審查交付給我們的程式碼」時，答案應該是可查的：設定檔中的家族清單、每個家族的部署方式與資料流向、SBOM 中的模型權重雜湊、每份報告的偏誤稽核區塊（雛型已有 ML-BOM 的格式與產生腳本，但自架模型的權重雜湊與簽章仍待平台團隊補齊）。若客戶要求排除某個家族（最可能是 GLM 這類中國關聯來源），第 7.3 節的可抽換性讓這在一週內可行；治理建議要求事先備妥替代家族的部署，並以實地換模演練證明（雛型已備妥三個冷備設定並完成 mock 排練，實地演練尚未進行）。但三個冷備設定的替代家族都是 DeepSeek，以它換掉 GLM 仍不能滿足「排除中國關聯模型」的要求；面對這類客戶，需要事先部署一個非中國關聯的自架家族。

## 第 22 章　成本模型

### 22.1 變數

成本由三個變數決定：bundle 的 token 數（雛型每次請求最多送約 40 萬字元，約 10 到 13 萬 token，視語言與 tokenizer 而定；更大的 repo 會切成多批，呼叫數隨批數倍增）、每次審查的呼叫數（單批的全庫審查約 45 次：情境建構 1 次、11 個面向 × 3 個 reviewer、否證與紅隊各數次、3 個 judge 各正反序 2 次；PR 審查若再只跑與變更相關的面向、裁減家族，可降到約 15 到 25 次，但雛型的增量審查目前只縮小 bundle、不裁減面向）、以及各家族的單價。Claude Opus 5.5 的 API 價格為每百萬輸入 token 4 美元、輸出 20 美元（舊版 Opus 5 為 5 與 25 美元）；Sonnet 5.5 為 2 與 10 美元；Fable 5.1 為 10 與 50 美元；改用區域或多區域端點另加 10%【已證實（直接讀取官方文件）｜B79、B128】；正式面板經 Bedrock 呼叫，實際單價以 AWS 帳單為準，本報告未查證。Gemini API 付費層的 `gemini-3.1-pro-preview` 為每百萬輸入 token 2 美元、輸出 12 美元（提示超過 20 萬 token 時為 4 與 18 美元），Batch 與 Flex 半價【已證實｜B148】；Batch 是否改變資料保留條件本報告未查證，正式設定不使用。自架家族的成本是 GPU 時數，與呼叫數的關係是階梯式的。

### 22.2 估算（以區間呈現）

以一次全庫審查、bundle 12 萬 token、Claude 承擔三分之一的呼叫（約 15 次，其中約 12 次帶整份 bundle，judge 只看盲化後的 finding）估算：Claude 的輸入約 150 萬到 180 萬 token、輸出約 15 萬 token，以 Opus 5.5 計約 9 到 10 美元（舊版 Opus 5 約 11 到 13 美元），以 Sonnet 5.5 計約 5 美元；prompt caching 對重複的 bundle 前綴可大幅降低輸入成本，快取讀取的價格一般是基礎輸入價的 10%，Opus 5.5 為 5%【已證實｜B79】。Batch API 雖然打五折，但不在 ZDR 範圍內，不能用於送往 Claude 的原始碼【已證實｜B81】。Gemini 承擔另外三分之一，以 3.1 Pro 的單價計約 5 美元。自架的 GLM 在約 15 次呼叫、每次約 12 萬 token 輸入下，GPU 時間取決於 IEC 端點的硬體與並行度，本報告沒有實測數字；初版估算自架兩個家族 30 次呼叫在單張 H100 或 H200 節點上約需數十分鐘。RepoAudit 的學術數據提供一個量級參考：每專案 0.44 小時、2.54 美元【已證實（ICML 2025）｜A86】，但它是單模型。

一個中型組織每日 50 個 PR、每晚 20 個全庫審查的量級下，雲端家族的月成本在數百到低數千美元之間，自架家族的成本取決於既有的 GPU 資產。這些數字的目的是量級而非預算：第五部的影子模式階段會產生真實的數字。

### 22.3 成本與去偏誤的取捨

第 16.6 節已指出成本壓力的方向。可接受的裁減是：PR 審查只跑與變更相關的面向、對 Low 嚴重度的面向用較小的模型（Sonnet 5.5、Gemini 的 Flash 級模型或 GLM 的較小型號）、對 bundle 做前綴快取。不可接受的裁減是：減到兩個家族以下、關掉反序 pass、讓 judge 看到分數以「節省」一次呼叫。治理建議把後三者列為政策。

## 第 23 章　從雛型到生產的差距

雛型證明的是行為：來源驗證會拒絕捏造、家族約束會被強制、盲審會抓到位置翻轉、分數可以重算（CVSS 4.0 計算器已對 FIRST 參考實作窮舉比對全部 base×E 向量）。它沒有證明的是效能：沒有任何真實模型的精確率或召回率數據。從雛型到生產需要：（1）以真實的三個家族在 seeded benchmark 上跑第一次校準；（2）實作第 13 章第 16 項的 bias sensitivity 測試；（3）把 L0 的工具從「有就跑」變成受控的版本；（4）把人工佇列接到組織的工單系統；（5）在影子模式下跑至少兩個月。截至 2026 年 10 月 6 日（v0.3.22），（3）已完成，工具以固定版本與雜湊安裝並驗證；（4）已在雛型中接上 GitHub issue 並把裁決寫回校準集，但尚無任何真實裁決；（1）的腳本與統計驗收（Alternative Annotator Test）已備妥，只以模擬家族跑過；（2）與（5）尚未開始。附錄E 的 prompt 套件涵蓋其中的（1）與（3），並以治理檢查追蹤（5）的導入階段。
