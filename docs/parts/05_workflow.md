# 第五部　使用流程

## 第 14 章　三種觸發模式

### 14.1 PR 觸發：增量審查

這是最常用的模式。開發者開 PR 後，GitHub Actions 以 `pull_request` 事件（絕不用 `pull_request_target`）啟動兩個 job。Job A 在只讀的 checkout 上執行 L0 工具並上傳 SARIF 為 artifact；Job B 讀取 artifact、以 L1 建構情境、呼叫 L2 到 L4，最後由 L5 產出 SARIF 上傳到 code scanning、Markdown 貼為 PR 評論、人工佇列寫入 issue 或看板。呼叫模型的 job 不執行 PR 中的任何程式碼。雛型附的 workflow（`.github/workflows/mara-review.yml`）只實作了這個模式的一部分：所有第三方 action 都固定到完整 SHA、每個 job 的 permissions 都明示為最小權限、所有 job 釘選 runner 映像並設逾時、L0 工具在獨立 job 執行且不允許失敗後繼續、SARIF 由另一個只有 `security-events: write` 的 job 上傳到 code scanning、推上 main 後由獨立 job 把人工佇列開成 issue（預設 dry-run）；但它不呼叫真實模型，也不貼 PR 評論，測試 job 以只讀 token、無 secret 的方式執行本 repo 自己的測試，並對內建漏洞範例以 mock 家族與預錄 SARIF 各跑一次全量與增量（`--base`）審查，用來驗證 pipeline 本身。真實模型的審查在能連到各家族端點的主機上執行（`docs/model-eval-runbook.md`），CI 中沒有切換成 live 模式的開關。

增量審查的範圍是「變更的檔案加上 L1 判定與其相關的檔案」，而非只有 diff。原因是 vibe-coded 程式碼的缺陷常在跨檔案的關係中：一個新加的路由本身沒問題，問題在它呼叫的既有函式從未做授權檢查。雛型以 `mara review --base <commit>` 啟用增量模式（diff 範圍為 `<base>...HEAD`）：保留變更的檔案、與它們有雙向 import 關係的檔案（Python 與 JS/TS 的相對 import），以及所有依賴清單與 workflow；其餘檔案一律在 coverage 中記錄為「增量範圍外」（`out_of_increment`），而非默默略過。變更的檔案若不在 bundle 中，審查標記為不完整。bundle 依每次請求 40 萬字元切成批次全部送審，不做優先排序；整個倉庫的上限為 1,600 萬字元，超過即標記審查不完整。增量模式縮小的是 bundle，不裁減面向或家族，所以 PR 審查的呼叫數與全庫審查相同，省下的是每次呼叫的 token。

### 14.2 夜間全庫審查

每晚對主分支跑一次完整的十一個面向。目的有三：抓 PR 審查因範圍限制漏掉的跨檔案問題；在依賴資料庫更新後重新評估依賴面向（EPSS 每日更新，KEV 隨時新增）；為校準迴圈累積資料。全庫審查的 token 成本顯著高於 PR 審查，第八部第 22 章的成本模型以此為主要變數。

### 14.3 手動深度審查

對高風險的變更（認證機制、資料庫 schema、密碼學、對外 API）由安全團隊手動觸發，可提高 judge 家族數、開啟第 16 項 bias sensitivity 測試、並把結果送人工複審。Endor Labs 的三專家代理產品會把安全架構的實質變更（新的 API 端點、認證邏輯的修改、開始收集新的敏感資料）標示出來，交給人深入審查【廠商主張｜A57】；本架構同意這個判斷，並把它落實為觸發模式而非 prompt 指示。

## 第 15 章　人工裁決佇列與校準迴圈

### 15.1 什麼會進人工佇列

雛型中以下情況會進人工佇列：judge 的多數裁決是 needs_human；該 finding 的家族一致度（agreement proxy）低於門檻（預設 0.4），代表家族之間顯著分歧；位置不一致、獨立 judge 不足、引用無法驗證、Skeptic 棄權、judge pass 無效、CVSS 向量無效，或 Skeptic 否證卻被評審團推翻（`skeptic_refuted_jury_overrode`）；被採納的 C 級 finding（單一家族）且嚴重度為 High 以上；以及在通過第 15.3 節的 Alternative Annotator Test 之前，每一個被管線拒絕的非 D 級 finding（`unsupervised_reject_unverified`）。Krippendorff's α 只在整批層級計算，因為單一 finding 只有兩到三個家族的票，α 在這個樣本量下沒有意義。人工佇列的每一項都附完整的中間產物：L2 的原始 finding、Skeptic 的理由、Red Team 的前置條件、每個 judge 家族正反序的裁決與理由。人工裁決者看到的是「誰說了什麼」，而 judge 看到的是盲化視圖；這個不對稱是刻意的，人類需要脈絡，模型需要隔離。

人工裁決有兩個用途。第一，裁決結果回寫成標籤，成為校準集的一部分。雛型以 `scripts/human_queue_issues.py` 把佇列開成 issue（以內容雜湊為 key，同一 finding 不重開），再把 issue 上的裁決同步回 `calib/decisions/`；截至 2026 年 10 月 6 日，這條路徑只在 dry-run 中走過，尚無任何真實裁決。這是第 15.3 節校準迴圈的資料來源之一，也是唯一能持續反映組織自身程式碼特性的來源。第二，重新審查同一份內容時，可用的裁決直接定案對應的 finding：人工判定優先於評審團，判為真陽性即採納（證據層級不變，閘門的阻擋規則照常適用），判為誤報即不採納；兩種情況下該 finding 都不再進佇列，也不再使審查不完整。裁決只綁定產生它的那一份內容（目標、revision 與 context 都相同），程式碼一改就重新送人工，因為一個版本的誤報在下一個版本可能是真的漏洞；完整審查與增量審查的 context 計算範圍不同，在其中一種審查上做的裁決也不會定案另一種審查的 finding。評審團原本的結論另行保留，校準量測的仍是管線本身而非人類，否則被管線丟掉、卻經人工確認的漏洞會從第 15.3 節 Alternative Annotator Test 的檢定中消失。工具結果不因人工裁決而消失，仍須經工具自己的分流程序；裁決者未受訓或裁決互相矛盾時不予採用，finding 維持待人工裁決。

### 15.2 審查疲勞與自動核准的陷阱

有二手報導稱 Anthropic 的內部測試發現人類審核者對 Claude Code 權限請求的核准率高達 97%，因此自 2026 年 8 月 14 日起把 auto mode 設為 Pro、Max 與 Team 方案新 session 的預設（Enterprise、API 與雲端平台仍須自行開啟）；同一報導還說，人類只攔下 13.6% 的危險指令，分類器攔下 89%【尚未證實（單一二手來源）｜A11】。這個數字若屬實，說明「人在迴路」在高頻、低差異的決策上會退化成橡皮圖章。本架構的人工佇列因此設計為高差異：主要是家族分歧、證據有疑或單家族高嚴重度才進入，且每項都附完整脈絡。例外是 AAT 通過之前的「不採納」：在管線證明自己可以替代人類之前，它的每個否決都需要人看，這段期間的佇列必然較長。若佇列長度持續超過團隊每週能處理的量，正確的反應是收緊門檻而不是加快核准。雛型在未結項目超過設定上限（預設 20）時自動把一致度門檻提高 0.1、不再把 C 級送進佇列，同時讓被採納的 C 級 High 以上 finding 直接阻擋閘門：收緊減少人工量，但不放行更多。

### 15.3 校準迴圈

校準迴圈每季執行一次，或在任何家族的模型升版後執行。輸入是三類帶標籤的樣本：公開的漏洞語料（OWASP Juice Shop、WebGoat、DVWA，以及 RealVuln 這類專為掃描器評測設計的資料集【第三方評論（preprint）｜A128】）、依第 2.2 節特徵自製的 vibe-coded 樣本（佔位式邏輯、未過濾輸入、機密外洩）、以及上一季人工佇列的裁決結果。輸出是四樣東西：每個家族在每個 CWE 類別的精確度與召回率；每對家族在錯誤上的重疊率（CAPA 或 pairwise agreement【B17】）；每個家族的 canary 回應率與拒答率；更新後的家族權重。

校準的驗收門檻採用《The Alternative Annotator Test》提出的統計檢定：在允許管線無監督地做出「不採納」決策之前，必須證明其判斷在統計上可替代人類標註者【已證實（ACL 2025）｜B70】。在通過這個檢定之前，雛型把管線的每一個「不採納」（D 級除外）都送進人工佇列，而不是抽查；政策 P8 只在校準證據證明檢定通過、且證據未過期時，才允許管線無監督地拒絕。截至 2026 年 10 月 6 日，雛型只有 mock 校準，AAT 尚未對真實模型執行，P8 因此維持關閉。

### 15.4 導入的三個階段

**影子模式（第 1 到 2 個月）。** 管線對每個 PR 執行但不評論、不阻擋，結果只給安全團隊看。目的是建立基線：誤報率、每 PR 的 finding 數、人工佇列的長度、token 成本。這個階段結束時應該有第一份校準報告。

**建議模式（第 3 到 5 個月）。** 管線在 PR 上留評論，A 級與 B 級的 High 以上 finding 標示為「建議阻擋」但不真的阻擋。開發者的反應（修、忽略、反駁）成為校準資料。雛型以設定檔的 `rollout.phase`（not_started、shadow、advisory、blocking）區分階段：影子與建議階段閘門失敗只記錄、不讓指令失敗，只有阻擋階段 `mara review` 才以結束碼 2 中止；貼 PR 評論需另行整合。Datadog 在介紹其 LLM 誤報過濾的文章中坦承，調得太積極的過濾 prompt 會漏掉真問題，最終是在漏報與噪音之間取平衡【廠商主張｜A62】；建議模式就是找這個平衡點的階段。

**門檻阻擋（第 6 個月起）。** 被採納的 A 級與 B 級 High 以上 finding 阻擋合併；佇列收緊時，被採納的 C 級 High 以上 finding 也阻擋。此外，任一面向分數低於 60、審查不完整（工具未執行、拒答、截斷、canary 回應等）、仍有待人工裁決的 finding，或有未處理的工具 error／warning 結果時，閘門同樣不通過：綠燈只代表「這次審查完整跑完且沒有阻擋項」。阻擋的 finding 必須附可重算的證據鏈（工具結果、逐字引用、家族裁決），開發者可以申訴進入人工佇列。第十部的治理建議把這三個階段對應到負責角色與時程。
